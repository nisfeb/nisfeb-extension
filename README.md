# Nisfeb for Brave and Chrome

Your Urbit ship from any page. One extension for the nisfeb apps that run on the ship: [auspex](https://github.com/nisfeb/auspex) (mail), [orrery](https://github.com/nisfeb/orrery) (a model of your world), [lattice](https://github.com/nisfeb/lattice) (pages and knowledge), [calendar](https://github.com/nisfeb/calendar) and [armillary](https://github.com/nisfeb/armillary) (inference), plus Tlon's chat. It talks to each over the ship's own HTTP API with the session cookie the ship's web apps use. There is no server in the middle and no account but the ship.

## Install

Load it unpacked: **brave://extensions**, turn on Developer mode, **Load unpacked**, pick this directory. Then open its **Options** page and give it two things: the ship's URL and its `+code`. Step by step, with your day as Brave's new tab and a troubleshooting table: [docs/setup.md](docs/setup.md). Agents working here read [AGENTS.md](AGENTS.md).

Connect asks the browser for permission to talk to that one origin (the manifest asks for nothing at install), then POSTs the code to `/~/login`, eyre's own login form. The answer sets the session cookie for that origin and the browser's cookie jar keeps it. **The code is used once and never stored.** A ship restart invalidates the cookie, and any 403 after that flips the status to signed out: connect again.

## What it does

Right-click a page, a selection or a link, or press **Alt+Shift+U** (or click the toolbar button) for the popup, which opens with the page's title, address and selection already in every card.

| | on the ship |
|---|---|
| **Send to Auspex** | the selection and the address as the body, the title as the subject, ships in To. **Send** posts `/apps/auspex/api/send`. **Edit in Auspex** saves it as a draft and opens the web client, whose composer has the contacts, the attachments and the rest. |
| **Send to a chat** | the page's title and address, with the selection quoted above them, as a message in a DM, a group DM or a group's chat channel, sent as you. The message is yours to edit first. The chat is picked by name from the ship's own list (`/~/scry/chat/dm`, `/~/scry/chat/clubs` and `/~/scry/groups/v3/groups`, the scries Talon reads), with the ones picked here last at the top; a ship can also be typed. The send is the poke Talon sends, `chat-dm-action-2` or `chat-club-action-2` to `%chat` or `channel-action-2` to `%channels`, on an eyre channel opened for it, and the card waits up to 15 seconds for the agent's answer: sent, refused (in the agent's words), or not confirmed, which means it may still land. |
| **Read in Orrery** | the selection, or the page's readable text when nothing is selected, handed to the ship's read channel, `POST /apps/orrery/api/read`, with the page as the source of every fact. The ship reads it as it reads a message: gate, extraction, grounding, filing, then proposals. The answer is immediate and the reading happens afterwards; the facts appear on the bodies the page names and proposals in your inbox. A page is sent once; sending it again is a second click. Needs orrery 59 or later. With an Orrery client key in Options the request is the key's (`Authorization: Bearer`, no cookie), so the facts carry the extension's own name and the key's scope bounds them; without one it is yours. |
| **Save selection to Lattice** | a private markdown page under `clips/`, `POST /apps/lattice/page-save`, with the title, the source and the date at the top and the selection quoted under them. |
| **Bookmark in Lattice** | `POST /apps/lattice/bookmark`: the ship's own browser bookmarks, the list its home page and address bar read. |
| **Archive page in Lattice** | the page as the browser holds it, `POST /apps/lattice/clip-html`, converted to markdown and filed under `clips/` by the ship. Paywalled and logged-in pages archive this way, since the ship never fetches anything. |
| **Add to Calendar** | an event (timed, or all day when no time is given) or a task due that day, the title as the name and the selection and address as the note. The same `add-event` poke the calendar page sends. |
| **Ask Armillary** | one question about the selection, or the whole page's text when nothing is selected, answered by the endpoint `GET /apps/armillary/api/inference` names: openrouter on a lease, the vendor ship's proxy otherwise. The key never leaves the worker. The answer can be saved to Lattice as a page. It needs an inference key on the ship: until Armillary there has a vendor and a key, the card says so and offers to open Armillary. |

**The omnibox.** Type `urb` and a space in the address bar. A `urb://~ship/path` address opens in Lattice's reader, anything else searches it, and the dropdown offers the ship's bookmarks and history as you type (`/apps/lattice/omni-suggest`).

Reads, clips, bookmarks and archives run from the menu on their own and report in a notification. Mail, chat, calendar and Ask need a recipient, a chat, a date or a question, so they open the popup on that card.

**Armillary in Brave Leo.** Leo's Bring your own model form can take your Armillary models, but no extension can fill it: Leo keeps its custom models in Brave's own settings. So Options, in Brave, has **Use Armillary in Brave Leo**: Leo's values read fresh from your ship (Label, Model request name, Server endpoint, API Key) with a copy button each, and a button to open Leo's settings. Only a lease can serve Leo, since Leo streams every answer and a vendor's proxy does not pass a stream on; with a proxy, or a lease switched off for an empty balance, it says so instead. The key is your ship's one lease, the one Talon uses: it is masked, and goes from the worker to the clipboard only when its copy button is pressed. Talon's own "Use in Brave Leo", as it is.

**Urbit links on web pages.** Turn on **Clickable Urbit links on web pages** in Options and the pages you read get links where they had text: an `urb://` address keeps its own address, for whatever handles `urb://` on this computer (Lattice, Talon on the desktop), with a **↗** beside it that opens the same address in Lattice's reader on your ship (`/apps/lattice?url=`); furum's `f/~host/board` and `f/~host/board/42` open on your ship (`/apps/furum/b/~host/board`), as they do in Talon. An `urb://` link a page already has gets the **↗** too. The script builds nodes and sets text, never HTML from the page; it leaves links, form controls, editable regions and code alone, skips your ship's own pages, and looks again at what a page adds or changes at most twice a second.

## Your day, as the new tab

**Today** in the popup opens a page with your day, drawn as Talon's home page: its greeting, Talon's sky clock, and cards from the ship with today's events and tasks (and, from six in the evening, tomorrow's first three), Orrery's open actions and what its model has cost this month, the mail waiting in Auspex, and your Armillary balance. Each card says plainly when its app is not installed, when you are signed out, or when the ship did not answer, and keeps what it last showed; one card failing never blanks another. **To arrange the cards,** press and drag one onto the place it should take. A long press or a right-click on a card starts arranging, as in Talon: each card shows arrows to step it and **×** to take it off the page, the header offers the cards taken off to put back, and **Done** ends it. The order and the cards taken off are kept in this browser, as Talon keeps its home page's per device. The greeting names you as Talon does: your nickname, or your @p when Talon is set to always show @p. Everything you set for the page is in **Options**, under **The day page**.

**It wears Talon's look.** With no custom theme in Talon, the page is drawn in Talon's own palette, light or dark as your system is (Talon keeps that choice per device, so it never reaches the ship). Light or dark can also be chosen in Options, as you have it in Talon. With a custom theme or an accent on in Talon, the page wears that: the worker reads Talon's settings from the ship's `%settings` (desk `talon`, bucket `ui-prefs`) with each refresh, and at once when the page has none yet, and the colours are derived from the theme's five as Talon derives them (`CustomTheme.kt`'s `customScheme`, through lattice's port). The text is in Talon's font: the system's sans, or the family chosen in Talon, whose files the worker fetches from grubbery once each (`talon/fonts/<id>.font`, checked against its sha256 name) and keeps in this browser. **Use my Talon theme and font** in Options turns all of it off, and Options says what was last read, so it can be held against Talon. A small script paints the last look before anything else loads, so a new tab does not flash.

**The sky clock** is the dial from Talon's home page: the day as a ring with noon at the top, the sun and the moon where they are, stars at night, and the ring coloured by the hour, the warmth, cloud and rain, with the time, the date, the sky, the temperature and the day's high and low inside. It needs a place for the sun's times and the weather: set one in Options, as a town or postcode (looked up at Open-Meteo when you ask) or as coordinates (never sent anywhere). Without one it shows an even day and no weather. With one, the worker asks Open-Meteo for its weather at most every half hour, five minutes after a failure, with the position rounded to two decimal places, about a kilometre. **That is the one request this extension sends anywhere but your ship**, and only once you set a place. Units follow the browser's language: 24-hour where its clock is, Fahrenheit where its region uses it.

**A background of your own.** Choose an image in Options and it sits behind the page, with the cards and the clock turned translucent over it. It is kept in this browser's Cache Storage, not on the ship, so each browser has its own.

**The search box** at the top searches with Brave Search on Enter, and **Research** starts Ask Brave's Deep Research with the same words (`search.brave.com/ask?q=…&enable_research=true`, the address Ask Brave's own research switch gives). Leo's page cannot be opened with words in it: it reads nothing from its address. Both open in the tab, or in a new one with Ctrl or Cmd.

**Browsing history into Orrery** is off until you turn it on in Options, which asks the browser for its history under that click. Then every hour the worker sends Orrery's read channel a digest of the sites visited since the last one: each site, how many of its pages, and the pages' titles. Never a page's text, never your ship's own pages, never a site you list, and never a private window's, which the browser keeps out of its history. It goes under the Orrery key when one is set, as Read in Orrery does, and Orrery reads it as it reads a message. An hour the ship did not take is carried into the next digest, six hours at most. One request to the ship an hour, and none while it is off.

**The assistant** is Talon's Assistant, run by the extension: a box on the page where you ask about your day or say what to do. The worker runs Talon's loop with Armillary's model (the one Ask uses, set in Options) and these of Talon's tools, in Talon's words: `list_events`, `create_event` (with Talon's repeats: daily, weekly on chosen days, monthly, the nth weekday of the month, yearly, every so many minutes), `update_event` and `delete_event` (a whole series, or one occurrence of it), `create_task`, `list_tasks`, `complete_task`, `orrery_brief`, `orrery_find`, `orrery_read` and `orrery_instruct`. The calendar's bodies are Talon's (`lib/calendar.js`, ported from `CalendarEdit.kt` with its tests), so an edit keeps every field it does not show, and one occurrence is changed the calendar page's way: the one-off added first, then the original skipped. Reads run on their own. A write is shown on the page in words, naming the event or task, and runs only on **Do it**; **Don't** is said to the model, which goes on without it. The last six exchanges go back to the model with each question, the history stays in this browser (the last fifty lines), and **New** clears it. A question costs the Armillary balance one model call per step (twelve at most), and each tool is one or two requests to the ship. Not yet: choosing among several calendars, mail and chat, and sharing the history with Talon's.

**Making it the new tab is your choice, in Brave's own settings.** The extension does not replace the new tab: a manifest override would replace everyone's, could not be switched off short of removing the extension, and would leave no way back to Brave's dashboard (`chrome://new-tab-page` under an override is Chromium's page, not Brave's). Brave can show your homepage as the new tab instead. Under **Appearance**, turn on **Show home button** and give it the page's address (Options shows it, with a copy button); under **Get started**, set **New tab page shows** to **Homepage** (Brave 153 keeps it there). **Dashboard** there brings Brave's own back. Chrome has no such setting, so in Chrome the page opens from the popup. [docs/setup.md](docs/setup.md) has it step by step.

| on the page | read from | source of the shape |
|---|---|---|
| **Today** | `GET /apps/calendar/window.json?from=&to=`, five days around now so today and tomorrow are in it in any zone; `GET /apps/calendar/config.json` once a day for the calendar's zone | calendar's `app.hoon` (`/window.json`, `/config.json`) and `calendar.js` (whole days in UTC date-space, the rest in the calendar's zone) |
| **Orrery** | `GET /apps/orrery/api/actions?status=open` and `GET /apps/orrery/api/generator/last` (`spend_month_micro`, from 0 in a new month), as the owner | Talon's `OrreryApi.actions`, orrery's `+serve-actions` and `+gen-record-doc` |
| **Mail** | `GET /apps/auspex/api/inbox?view=inbox&limit=20`: the Inbox's unread count and the unread subjects on its newest page | auspex's `+serve-inbox` and `+entry-json` |
| **Armillary** | `GET /apps/armillary/api/account`; the balance and the vendor are kept, and nothing else of that answer (it carries key secrets) leaves the worker | armillary's `+serve-my-account` |
| the look | the scry `/~/scry/settings/bucket/talon/ui-prefs.json` (a 404 is the built-in look), `/~/scry/contacts/v1/self.json` only for a profile-colour accent, and `GET /grubbery/api/file/talon/fonts/<id>.font` once per file of an installed font | Talon's `SettingsSyncImpl` (each value a JSON string), `CustomTheme.kt`, `ThemeSettings`, `AccentSettings`, `AppFonts.kt` |
| the clock | Open-Meteo, not the ship: `api.open-meteo.com/v1/forecast` for the place set, and `geocoding-api.open-meteo.com/v1/search` when you look one up | Talon's `OpenMeteoWeather.kt` and `OpenMeteoPlaces.kt` |

**What it costs the ship.** The page never fetches. It draws the last snapshot from the extension's storage at once and asks the worker to read the ship, and the worker reads at most once every five minutes however many tabs ask: the time of the last try is stored before the reads start, a try that failed counts, and a read already running is shared. The page asks again only when it comes back into view, or every fifteen minutes while it stays in view. One refresh is **five requests to apps** (calendar, orrery twice, auspex, armillary), each of which is an event on the ship and about a second of its one thread, and **one scry** for Talon's look (two when the accent is the profile colour). The mail listing is the heaviest, since auspex walks every stored message for it. Once a day a refresh adds the calendar's `config.json`. So the ceiling is twelve refreshes, sixty app events, an hour, whatever the number of tabs. The clock costs the ship nothing.

## Ceilings

- **No held connection, no live counts.** Nothing here holds the ship's change beacon. Mail notifications belong to the desktop app and the Thunderbird add-on, which already do that job. The popup makes requests only when you open it and only for the card you use. The day page reads at most once every five minutes and shows the time of its last read; what changed since then shows on the next.
- **The day page is a snapshot.** Counts are the ship's at the last read. Mail subjects are the unread ones among the newest twenty threads, so an older unread thread counts but is not named. An Orrery action links to Orrery's inbox, which has no address for one action. A theme changed in Talon shows on the next read.
- **The clock moves by the minute.** Talon's dial slides its sun and fades its colours; this one steps to each new minute and forecast. It has no device location: the place is typed. The background image is kept as chosen, not scaled down.
- **Ask needs a second permission.** The answers come from a third origin, so the first Ask on a ship asks for that origin under your click. Refuse it and the request still goes out; it works if that endpoint allows browsers in.
- **Manifest v3**, so the worker is asleep between clicks. Every action carries what it needs in the message.
- Recipients are typed, not picked. The web client's contacts are one click away under **Edit in Auspex**.
- **Chats are listed by name, not by when they last spoke.** The ship's list of DMs has no order and the scry that has one is the heaviest the ship serves, so "recent" means the last eight picked here. The list is kept for ten minutes per browser session; a group joined since shows after that, or can be typed. DMs are named by ship, not by contact nickname.
- **A message is plain text and links.** Addresses become links; a `~ship` stays text rather than a mention (a page's text should not notify anyone), and Markdown and fenced code go as written.
- **Urbit links need every site.** A script that reads page text has to run on every page, which is the browser's broadest permission. So it is not in the manifest, which would ask everyone for it at install; it is registered from Options, and asks for access to all sites under that click. Turning it off stops the script; the browser keeps the site access until it is removed in the extension's settings. Content scripts get no view of the extension's stored settings (the Orrery key among them), and the only thing one may ask the worker is the ship's address.

## Testing

`npm test` covers the pure parts: ship names, page names, the calendar bodies, what a selection becomes, and for chat the three poke bodies, the story, the post id, the chat list from the scries' answers, and the channel round trip (the poke, its answer off the event stream, the channel deleted after) against a stand-in for eyre. For links, what counts as an `urb://` address or a furum shorthand and where each opens, pinned to Talon's own patterns. For the day page, the refresh throttle, a failed card keeping its data, the status, each app's answer read as its source writes it (today in the calendar's zone with whole days in UTC, the unread mail, the open actions and the month's spend, a balance that keeps no key), each read's address and the failure words. For the look, the Oklab mixing, `customScheme`'s roles, which theme is on, and the accent in each mode. For the clock, Talon's own sky clock tests case for case (sun, moon, sky mix, weather codes, the forecast parser) and the port's own: a place across the world on its own clock, the rounded request, the place search, the labels, and the cloud and star rules.

`npm run today` checks the day page in a throwaway headless Brave against a stand-in ship, with no ship and no cookie: the page with no ship, a stored snapshot drawn without a request, each card's words for a missing app, a 403, a 502 and a dropped connection, a refresh that asks each source once at its own route and a second tab that asks nothing, Talon's custom theme set on the page and off when turned off (and the built-in look on a 404), the clock drawn with no ship and no place and asking for nothing, a stored forecast drawn and not fetched again, a background chosen, kept for a new tab and removed from every tab, and a refresh that finishes after the tab closes.

`npm run smoke` runs the extension against a dev ship in a headless Brave (the day page's refresh among its steps): it stages a copy, launches once so the scratch profile records it, writes the ship's host permission into that record (Brave withholds a command-line extension's manifest host permissions, and without the permission the fetches are cross-site and carry no cookie), launches again with the session cookie set, drives the worker's handlers over the devtools protocol, checks each result against the app's own API, and removes what it made. Every ship request is capped at a minute, so a dev ship busy with another gate fails the run on time rather than on substance. It needs `SHIP` and `COOKIE_FILE` in the environment; `scripts/smoke.js` says how to mint the cookie. The cookie file is a secret: keep it out of the repo.

## Family

Talon on the phone, Auspex in Thunderbird and on the desktop, Lattice on the desktop and as a filesystem, and this in the browser. All of them are the same rule: the ship stores it, the client is a window on it.
